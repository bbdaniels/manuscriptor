Read `Manuscriptor/Tasks.md` at session start. The design is `Manuscriptor/plans/2026-07-22 - Phase 1 Design.md`; verified findings and decision rationale are in `Manuscriptor/Technical Notes.md`. Read the design before implementing a milestone, because most of the non-obvious constraints are recorded there rather than in the code.

## What this is

A live manuscript editor. LaTeX renders to a page where every block is addressable back to its source bytes, so a margin comment or a direct edit resolves to a real byte range rather than to a page number and a highlighted phrase.

`manuscriptor serve <dir>` works end to end today. The drain (`proc` and the wake job) is the piece still missing, so chats land in `comments.jsonl` and nothing reads them.

## Invariants

**Context wide, unit narrow.** A worker may read as widely as it needs and may only ever write one block. This is what makes running edits live acceptable. Do not add a code path that writes more than one block per operation.

**A BLOCK is the unit of an agent's write. An EDITOR BOX is not, and `splice._carried` is the only thing allowed to say how far a box reaches.** The author types into a box; the file keeps blocks; and the two stop agreeing the moment a save SPLITS the paragraph he is in. The page renames his box onto the first half -- correctly -- and may not take his text away from him while his cursor is in it, so from the next save onward the box holds a passage the file is keeping as several blocks. Writing it over the first of them leaves the rest standing underneath, and every further save does it again: on 2026-08-13 an author formatting a four-paragraph passage a blank line at a time put FOUR copies of it into qutub-ayush's `main.tex`, each with one blank line fewer than the one above, with the server answering `saved` every time. Refusing the save is not the alternative -- his formatting is not a mistake, and a box that can never be written again is a paragraph he is locked out of. So a save may replace the blocks after its target that it can be SEEN to still carry: contiguous in the file, everything before the last of them matching exactly, and the last one exactly or nearly (it is the one he may still be typing in). A paragraph he genuinely ADDED matches nothing below it and is inserted, which is the half of the rule that keeps the other half from eating the section heading below. Agent writes hand `splice` one block and no `following`, so nothing about their unit moves.

**The server has zero knowledge of Claude, and Claude never talks to the server.** They communicate through the `.tex` tree and `comments.jsonl`, and nothing else. Do not add an LLM call inside `manuscriptor/server/`, and do not add an HTTP client to the drain.

**`comments.jsonl` is append only.** Two processes write it. A rewrite introduces conflicts that appending cannot have. State changes are new records, never edits to old ones.

**Block identity is content derived, never positional.** Line numbers move the moment anything above them changes.

**Never write to a generated ARTIFACT -- and a block is only one kind of artifact.** A file written by analysis code must refuse the write and name its producer instead. This invariant was widened deliberately on 2026-08-04, from blocks alone, when the same failure turned up one file over. The original case: `tables/*.tex` produced by an R or Stata script, where editing hardcodes a result and violates the standing rule against typing numbers into LaTeX. The case that widened it: covet-india's `sample.bib` is exported from Zotero by `manuscript/make-bib.py`, and `plan_citation` appended an entry to it. The appended entry dies at the next `make bib`; the `\citep{...}` spliced into `main.tex` survives -- a citation with no bibliography entry, a broken build the author did not cause and could not see coming. Worse, the insert minted its own cite key while the generator gates on Zotero's `citationKey`, so the regeneration would have failed its resolve-to-exactly-one check on a key nothing in the library carries. The refusal is a BLOCKING check naming the producer and the remedy the file's own header states, never a silent skip: over-claiming a hand-maintained `.bib` would refuse every legitimate insertion, so the author has to be able to see which file, which producer, and what to run instead.

**Provenance is decided in `server/producers.py` and nowhere else, whatever the suffix.** One function, `provenance()`, answers "is this written by something other than the author" for a `.tex` block and a `.bib` alike; callers ask it and never re-derive an answer. A file's own `GENERATED FILE` / `DO NOT EDIT` header is a second SIGNAL feeding that one decision -- a producer scan can only see scripts it can reach, and a Makefile rule or a generator in another repo is invisible to it -- and it must never become a second implementation living somewhere else. Never infer "generated" from a path or a directory name. That guess once marked 74% of the reference manuscript uneditable, because its hand-written prose appendices are also not the root file. `segment()` decides only whether a block can be spliced as one byte range; that is a different question and the two must not be folded together again.

**Ids are content-derived, so an edit renames its own block.** Anything comparing block ids across two builds must go through `rematch` and carry the rename onward, or drafts and chats keyed to the old id are silently orphaned. This bug has already been introduced once, in the server's patch diff.

**LaTeX table-structure repair -- column-type normalization AND header-row identification -- is decided in `render/tables.py` and nowhere else, in this repo or any other.** This invariant was widened deliberately on 2026-08-03, from column types alone, when the second repair was added. Both answer the same question -- what does this LaTeX table actually say -- and both can only be answered while the LaTeX still says it, so they get one home rather than two.

The header half: pandoc's LaTeX reader promotes at most ONE row into `<thead>`, so a table whose header is two rows deep comes back as body rows only, `theadCount` 0, and every sticky-header and header-rule style switched off -- 31 of the 44 tables actually reachable from the served documents. (A `.tex`-file count says 72 of 243; most of those files are never reached by a render, and the rendered count is the one that matters. Pandoc also emits no `<thead>` for a SINGLE-row header with no closing rule, which is why the rendered number is not simply the multi-row count.) `mark_header_rows` marks those rows before pandoc reads them, using the full-width rules the author wrote, and `render/postprocess.py` may only CARRY that marking into `<thead>`. It must never infer which rows are headers: covet-india's Table 1 puts `\multicolumn{6}{l}{\textit{Patna}}` in the middle of its body as a panel label, indistinguishable from a header row by content and not one. In the LaTeX the rules say which is which; in the HTML they are gone. The mark goes INSIDE a leading `\multicolumn`'s content group, because a cell that begins with `\multicolumn` is a spanning cell to pandoc and anything in front of it costs the span and the words inside it, at exit 0.

The column-type half: stripping a `\newcolumntype` and rewriting the specs that used it are one operation, and half of it is worse than none: strip alone and a longtable degrades into prose at exit 0, or estonia-ecm's redefined `r` -- ragged-*right*, so left-aligned -- renders right-aligned, backwards and silently, with the table intact so no structural guard fires. That is why a partial re-implementation is the hazard rather than a missing one. There were two copies on 2026-07-29, this one and a standalone written that afternoon in the Word submission skills; diffed over 3,477 `.tex` files they disagreed on eight, and the wrong copy was this one, losing estonia-ecm's balance table to a `\multicolumn` broken across a line. The second copy existed for about two hours. That is the argument, not a footnote to it: two implementations of this operation did not need months to diverge on real manuscripts, they needed an afternoon. The skills now import this module and fail loudly when it is absent, because a skipped normalization ships degraded tables into the `.docx` a journal submission is built from. A guard in `tests/test_render_tables.py` fails if anything re-implements EITHER half, and it scans the whole of `~/.claude/skills/` as well as this package -- the copy that existed lived under `submission/`, but the next one has no reason to.

**A marking is a message to `render/postprocess.py`, so it is minted only on the path that runs one, and `render/pandoc.py` is where that is decided.** Two consumers read the normalization and only the page has a postprocess: `normalize_for_viewer` mints the title-block tokens and the header mark, `normalize_for_pandoc` mints nothing, and both run the same repairs in the same order because a `.docx` wants a repaired table as much as the page does and a `\newcolumntype` aborts pandoc for both. Sharing the marking is not a cosmetic slip -- `server/compile.py` writes that output to `inter.tex` and hands it to pandoc and on into the file a journal receives, so every Word file the button has ever produced carried the sentinels as literal glyphs: 250 of them on estonia-ecm, 247 being `⟦MXTHEAD⟧` inside table header cells, at exit 0 with the tables intact so nothing looked wrong (found 2026-08-17). What is NOT viewer-only is the front-matter REWRITE -- pandoc reads `\title` into document metadata and an HTML fragment shows metadata nowhere, so dropping it would ship a manuscript with no title on it; only the tokens saying which construct it was are withheld. The guard is a sweep on the sentinel brackets rather than on the four tokens known today, in `tests/test_render_pandoc.py` and end to end on a real `.docx` in `tests/test_compile.py`, so the next viewer-only marking added to the shared path fails there instead of in a submission.

**What belongs to an exhibit card is decided in `render/cards.py`, by BLOCK, and never by what a paragraph says.** An exhibit's notes define the stars, state the clustering and name the sample; the PDF sets them inside the float in small type, and the page set them outside it at body size and unclickable. Pandoc returns a `\begin{table}` float as one element and its trailing `\footnotesize` paragraph as the NEXT one, and the block's `data-mx` rides on the first -- so a click on qutub-ayush's `tab:main` notes resolved to no block at all, for bytes that are unambiguously in that block. The rule is the BLOCK, and it is a carry rather than a guess: the author wrote the exhibit and its notes into one block, `server/blocks.py` computed that extent from the source bytes and `render/anchors.py` wrote it into the HTML as the markers this pass reads back. Never match the label. The corpus spells it `Notes:`, `Note:`, `\underline{\textbf{Notes}}:`, and nothing at all, and dsp-bias and qutub-india put the same content inside `\caption{}` instead -- a word match would find some, miss more, and claim a body paragraph the first time a section began "Notes on the sample follow."

This is the header-row rule's shape with its hazard inverted, and the difference is worth stating because it is what keeps the Word path out of it. There, the truth lives only in the LaTeX, so the marking must happen before pandoc and `postprocess` may only carry it. Here the truth SURVIVES pandoc, because block extent is the marker, so no LaTeX-side marking is needed at all -- and that matters, since `server/compile.py` hands `normalize_for_pandoc`'s output straight to pandoc and on into the `.docx`, where a minted token ships as a literal glyph in a journal submission. The fold runs after `_wrap_tables` and never before it, because a captioned table only becomes a card at that step. The block scope also draws the far line, and drawing it is the point rather than a limitation: covet-india and sdi-caseloads write no floats, so their thirty-four exhibits keep the note in a block of its own, and folding it would put two block ids on one element, which is the one thing `harvest` refuses. A guard in `tests/test_exhibit_notes.py` fails if anything else spells the classes.

**And the exhibit is found by DESCENT, because pandoc's element tree is not one tree.** The fold matched the exhibit at root level, which is the shape pandoc 3.10.1 emits; 3.1.1 wraps a LABELLED table float in a `<div id="tab:main">`, so the block's `data-mx` lands on the div, the exhibit is its grandchild, and the notes are the div's next sibling rather than the figure's. The author's own PATH puts `/usr/local/bin` ahead of `/opt/homebrew/bin`, so his server is the 3.1.1 one: qutub-ayush, qutub-india and dsp-bias rendered ZERO folded notes on the machine he reads from while the corpus check, run against 3.10.1, reported them folded and the fix shipped (2026-08-18). Never assert a render property from a build in this shell alone -- the shell and the server can resolve different binaries -- and never match an element by its position in pandoc's output when the block already says which element it is. `_exhibit_within` descends through a wrapper that holds the exhibit and nothing else, and refuses a wrapper carrying prose of its own, which is the author's layout rather than ours.

**Unwrapping an environment means closing the group it was closing.** `\begin{env}`/`\end{env}` are a group, so LaTeX forgives an unbalanced brace inside one, and estonia-ecm's appendix spends that allowance in both directions: `\scriptsize{` is opened in every `tablenotes` and closed in none, and `tableE1_coding`'s notes were commented out one line at a time until only the closing `}` was live. `_unwrap_environment` drops the delimiters, and each of those then failed the ENTIRE manuscript at pandoc -- `unexpected \end` and `unexpected }` -- at a line the author had never touched and could not have suspected. `_balanced` closes unclosed openers where the `\end` stood and drops closers that opened nowhere, comment-aware, because three of the four braces in that table are behind a `%`.

**One observer per directory, and `server/watch.py` is what enforces it.** Watchdog's fsevents backend keys its stream registrations in a PROCESS-GLOBAL table on `(path, is_recursive)`, so two `Observer()` objects on one directory are not independent -- they are one registration plus a `RuntimeError` thrown inside the emitter thread, where nothing catches it. The second watcher then exists, answers `stop()`, and never delivers an event. That is how `serve` spent weeks holding a dead watch on `.manuscriptor/agent`: the feed and the ledger are two files in one directory and both legitimately need watching, so both call sites were correct and the defect was a level below them. The live history push was simply off, and the traceback at boot read as cosmetic. Callers ask for a file or a tree; `watch.py` shares the underlying observer, fans out to every handler, and refcounts the teardown so the first leaver cannot unwatch the others.

**The served tree is not the whole of what a render depends on, and `render/graphics.py` says what the rest is.** A `\graphicspath` entry may name a directory outside the manuscript -- qutub-ayush's is `{{../outputs/}{figures/}}`, written by the analysis code beside the paper -- and a figure APPEARING in one changes what an `\includegraphics` resolves to. Before the file exists the include resolves to nothing and is left exactly as the author wrote it, on purpose, so the page holds `<img src="f-did-components">`; the export is what makes that wrong, and for as long as `serve` watched only `session.dir` the export was not an event at all. The broken image then survived every reload and would have survived until an unrelated `.tex` edit happened to rebuild. Observed live 2026-08-17: server up at 11:41, figure exported at 15:03, page still unresolved at 15:05 with every other figure on it correct. `graphics.search_dirs` is the one answer to "which directories does this document read figures from" -- the same list `find` walks, through one `_search_order` -- and `app.FigureDirWatches` watches the ones the tree watch does not already cover, re-arming after every build so the watches follow a document switch. Watching a directory is not permission to read it: `refresh_asset`'s rule that only a build stages an external figure is untouched. Guards in `tests/test_figure_appears.py`.

**A rebuild the page is not told about is a rebuild that did not happen.** `on_assets_change` used to rebuild and then broadcast only the cache-busting `assets` frame, throwing the diff away -- right for a regenerated figure under LaTeX that did not move, and wrong the moment the rebuild changes any HTML, which is exactly the appearing-figure case above: the server had the resolved `src` and the open page kept the broken element. It is one operation, "rebuild and tell the page what moved", so there is one implementation of it and `on_assets_change` calls `on_change(refresh_assets=True)`.

**The rebuild never runs on the event loop, and nothing the watcher starts may fail in silence.** Both halves are about the same stretch of time -- between the author's keystroke and his paragraph changing on screen -- and both were measured rather than read. A rebuild is half a second of pandoc, hashing and file IO on a real manuscript, and called inline it stopped the ENTIRE server for that whole stretch: measured at 763ms of a 1.1s round trip on qutub-ayush, during which no route answered, no frame went out and no image was served. A page with no figures never noticed, because it asks the server for nothing while the author types; a page with eight of them asks constantly, which is why this surfaced the day that manuscript's figures started resolving and not before. `on_change` and `on_assets_change` hand `rebuild` to a thread; the session lock still serializes them, so only the thread changes. And every coroutine the watchers start goes through `Session.spawn`, because `run_coroutine_threadsafe` returns a `concurrent.futures.Future` and -- unlike an `asyncio` one -- it never logs the exception nobody retrieves. Anything raised after the rebuild therefore vanished completely: the build advanced, the socket stayed open, the page kept the paragraph the author had just rewritten, and no line of output anywhere said why. `spawn` retrieves the exception and `Session.fail` states it in both places it has to be stated, the page and stderr. Guards in `tests/test_on_change_delivery.py`.

**Everything on disk goes through `server/paths.py`, and nowhere else names it.** The layout was once fourteen literal spellings of `root / "build" / "manuscriptor"` across five modules, which made it unchangeable in practice. One module answers "where does Manuscriptor keep its files"; a guard in `tests/test_paths.py` fails if anything else spells it.

**The hidden directory writes its own `.gitignore`, and the rule hides itself.** `.manuscriptor/` sits inside the manuscript directory, which is nearly always a git working tree the author cares about. Serving a paper must never make `git status` grow, so the ignore file covers everything including itself. `comments.jsonl` is the single exception, because a coauthor needs the review record.

**Three tiers, and only one of them is disposable.** `cache/` is regenerable by rebuilding and is the ONLY thing `manuscriptor clean` may remove. `drafts.json` and `agent/` are durable but private. `comments.jsonl` is durable and tracked. Do not move anything durable under `cache/`: `clean` was once `rmtree` on the directory holding `drafts.json`, so running it destroyed unsaved text no rebuild can reconstruct.

**Compiling writes only into the cache, except the deliverable.** The `.aux`, `.log`, `.bbl` and `.blg` stay hidden; the reference manuscript has several of those COMMITTED, so writing them beside the source rewrites tracked files. The finished PDF is copied out beside the `.tex` on success and ONLY on success, since replacing a good PDF with the output of a compile that died in pass 2 leaves a file that still opens and is quietly wrong. A read-only serve withholds even that copy.

**Which `.aux` a document's numbers come from is decided in `render/refs.py`, by freshness, and nowhere else.** There are two files with a claim -- the compile cache's and the one beside the source that only the author's terminal `make` writes -- and for as long as both existed, `compile.py` wrote one and `build.py` read the other. So on covet-india the author pressed Compile, it succeeded, and every `\ref` on the page still read `??`: the button was structurally incapable of resolving a cross-reference, for every manuscript, always, with nothing raising. `refs.choose_aux` takes the NEWER of the two, never the one that is ours, because an author who has just run `make` has better numbers than our last compile. A guard in `tests/test_aux_choice.py` fails if any module derives the path itself. And because the compile writes into the hidden cache, which the tree watcher ignores on purpose, a SUCCESSFUL compile redraws the page from its own route -- a failed one redraws nothing, since its `.aux` is whatever the run died holding.

**A compile the author did not ask for never delivers, and never runs twice on the same question.** Stale numbering compiles itself in the background (`compile.auto_compile`, triggered where `Session.on_change` finishes a rebuild, and once at boot), because a `\ref` the page prints as `??` is a number LaTeX already knows. Three properties make that safe and each has a guard in `tests/test_auto_compile.py`. It passes `deliver_out=False` ALWAYS: copying a PDF beside the `.tex` is the write the button's press authorizes, and an unrequested run has no such authority -- read-only or not, the deliver is the difference between the tool compiling for its own display and the tool writing into the author's tree. It triggers on the NUMBERING SIGNATURE -- the labels declared, the refs used, the counter bindings -- and never on typing, so prose costs nothing and adding a `\label` costs one run. And it attempts a given signature ONCE, success or failure, because a failed compile leaves a `\ref{typo}` exactly as unresolved as it found it and re-triggering on that is an infinite loop with a subprocess in it. A failure refreshes nothing, opens no panel, and still says so in the compile panel in its own words.

**`tidy` reports and does not sweep.** It runs against real manuscripts. Whether a file is regenerable is decided by its suffix; whether removing it is safe is decided by asking git. Never conflate the two: dsp-bias tracks `main.bbl` and `supplement.bbl`, so a suffix-based sweep would delete two committed files.

## Never drive the editor against a real manuscript

`serve` is read-write. Automated interaction against a live manuscript WILL
eventually write to it: on 2026-07-22 a browser-driven verification pass left
`\footnote{}\footnote{}` at the start of a paragraph in estonia-ecm's main.tex.
It was recoverable only because that file happened to be clean in git.

Copy the manuscript to a scratch directory and point `serve` at the copy for any
test that clicks, types, or dispatches events. The real manuscript may be served
for reading and screenshots, and nothing else.

## Testing

Watch every guard fail before trusting it. A test that has never failed proves nothing, and a skipped test is not a pass. The tests that matter most: flatten resolves nested includes with exact offsets; block ids survive an edit above them; sentinels round-trip through pandoc into the correct position; a splice to block N changes only block N's bytes, and an editor box that has split into several changes those and nothing past them; a comment on block 40 still resolves after block 3 is rewritten.

**A test may not write a websocket frame.** For a long time none did, and the whole live push path was untested while the boot path was asserted everywhere -- so the server rebuilt correctly and the open page stayed wrong, in four places at once, under a suite that passed. `tests/pagedriver.py` loads the page the server renders, runs the real `viewer.js` in it, and hands it frames the server built (`_diff`, or whatever `broadcast` was handed); assert on what the page holds afterwards. It needs node and jsdom -- run `npm install` in `tests/js` -- and `tests/test_live_frames.py` SKIPS without them, so check that it ran.

## Verifying rendered output

Arc is effectively always running, and launching a second instance is prohibited. Probe `curl -s 127.0.0.1:9222/json/version` and connect to the live session via the chrome-devtools MCP. Point a tab at the running server rather than at a file, and call `resize_page` to 1440x900 before screenshotting, since retina defaults exceed the 2000px image limit.
